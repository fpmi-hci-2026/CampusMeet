## 1. Контекст и бизнес-цель (Intent and The Why)

В рамках лабораторных работ №1–6 команда CampusMeet разработала концепцию, информационную архитектуру, BDD-спецификации, REST API контракты (OpenAPI 3.0), дизайн-систему в Figma (22 макета) и провела юзабилити-тестирование. 

Лабораторная работа №7 является ключевым практическим рубежом курса, на котором осуществляется **переход от проектной документации к работающему программному обеспечению**:
1. Разработка серверного приложения с реализацией бизнес-логики управления ключевыми сущностями локальных университетских митапов (пользователи, события, квоты мест, билеты с динамическими QR-кодами, валидация прохода).
2. Формирование интерактивной документации API (OpenAPI 3.0 / Swagger UI).
3. Создание первых рабочих интерфейсов: первой страницы веб-приложения (каталог афиши мероприятий) и первого экрана мобильного приложения (билет участника с QR-кодом), взаимодействующих с реальным API.
4. Внедрение непрерывной интеграции (GitHub Actions CI) со строгим контролем качества кода (Quality Gate SonarQube/SonarCloud, линтеры, автоматические тесты `pytest`).
5. Контейнеризация сервисов в Docker Compose и подготовка облачного развертывания на Render.
6. Составление всестороннего академического отчета с фиксацией вклада каждого участника и истории коммитов.

## 2. Цели, границы и анти-цели

> [!IMPORTANT]
> **Критическое требование к Git:** Все изменения в репозиториях (`CampusMeet-Server` и `CampusMeet`) необходимо коммитить структурированно и логично, но **КАТЕГОРИЧЕСКИ НЕ ДЕЛАТЬ `git push`**! Отправку в удаленный репозиторий пользователь выполнит самостоятельно.

### Цели (Goals):
1. **Серверное приложение (FastAPI):**
   * Модульная архитектура: роутеры (`auth`, `events`, `tickets`, `venues`, `checkin`), схемы Pydantic v2, сервис данных SQLite/SQLAlchemy.
   * Реализация управления сущностями: вывод единичных записей (`GET /events/{id}`, `GET /tickets/{id}`) и списков с фильтрацией и пагинацией (`GET /events`, `GET /tickets/my`, `GET /venues`).
   * Реализация ключевой бизнес-логики CampusMeet: контроль лимита вместимости аудитории (`capacity_limit`), лист ожидания (Waitlist), генерация криптографического HMAC-токена билета и верификация чекина волонтером с защитой от повторного прохода (HTTP 409).
   * Автоматическая генерация интерактивной документации Swagger UI по адресу `/docs` и ReDoc по адресу `/redoc`.
2. **Первая страница веб-приложения:**
   * Каталог афиши университетских событий с карточками, фильтрами по статусу и типу (митап, хакатон, воркшоп), строкой поиска и модальным окном быстрой регистрации.
   * Прямая интеграция с бэкендом через `fetch('/api/v1/events')`.
3. **Первый экран мобильного приложения:**
   * Адаптивный мобильный экран персонального билета участника с динамическим обновлением QR-кода, информацией об аудитории и статусом («Действителен», «Использован»).
   * Прямое получение данных билета через `fetch('/api/v1/tickets/{id}')`.
4. **Автоматическое тестирование и контроль качества:**
   * Не менее 25 автоматических тестов `pytest`, покрывающих аутентификацию, CRUD операций, фильтрацию списков, отсечение овербукинга и валидацию чекина.
   * Конфигурация линтеров Flake8/Black и файла `sonar-project.properties` для статического анализа SonarQube/SonarCloud.
5. **Инфраструктура и CI/CD:**
   * `Dockerfile` для серверного приложения.
   * `compose.yaml` для локального запуска полного стека одной командой `docker compose up --build`.
   * Пайплайн GitHub Actions (`.github/workflows/ci.yml`), выполняющий сборку только при успешном прохождении линтеров и тестов.
   * Манифест `render.yaml` для облачного развертывания.
6. **Академический отчет и интерактивный портал:**
   * Полный отчет в формате Markdown [`docs/reports/Lab7_report.md`](file:///Users/shvarsman/developer/PCMI/CampusMeet/docs/reports/Lab7_report.md) по структуре методички кафедры ТП БГУ.
   * Интерактивная страница [`docs/pages/lab7.html`](file:///Users/shvarsman/developer/PCMI/CampusMeet/docs/pages/lab7.html) на GitHub Pages с живым Swagger-встраиванием, инспектором запросов и демо-экранами.

### Границы и не-цели (Non-Goals):
* Полноценная интеграция с банковскими шлюзами эквайринга (CampusMeet ориентирован на бесплатные студенческие события и внутренние университетские квоты).
* Развертывание промышленного кластера Kubernetes (в рамках учебного курса требуется Docker Compose и облачные PaaS, такие как Render/Vercel).

### Анти-цели (Anti-Goals):
* Фиктивные mock-заглушки без валидации параметров и сохранения состояния.
* Игнорирование ошибок линтеров или отключение проверок в CI пайплайне.
* Нарушение дизайн-системы True Black AMOLED, утвержденной в ЛР5.

## 3. Рассмотренные подходы (Approaches)

### Подход 1: Модульный сервис на FastAPI + Pydantic v2 + встроенные клиенты (Выбранный)
* **Архитектура:** Использование FastAPI, Pydantic v2 и SQLite (с поддержкой полной PostgreSQL-схемы из ЛР4).
* **Клиенты:** Веб-афиша и мобильный билет поставляются как статические модули (`web/` и `mobile/`), обслуживаемые FastAPI или запускаемые автономно.
* **Преимущества:** Нативная генерация спецификации OpenAPI 3.0 и Swagger UI, строгая валидация типов, асинхронная производительность, простота развертывания в Docker.
* **Решение:** Выбран как основной.

### Подход 2: Расширение рукописного mock-сервера из ЛР4 на `BaseHTTPRequestHandler` (Отклонен)
* **Причина отклонения:** Ручная обработка заголовков, query-параметров и сериализации JSON лишена валидации схем, не предоставляет Swagger UI «из коробки» и не соответствует квалификационным требованиям к бэкенд-разработчику 4 курса кафедры ТП.

### Подход 3: Переход на Node.js / Express (Отклонен)
* **Причина отклонения:** Вся кодовая база ЛР4 (модели, скрипты инициализации SQLite/Postgres DDL, тесты) написана на Python. Смена языка неоправданно увеличит трудозатраты без выигрыша в функциональности.

### 4.3. Спецификация API и совместимость с контрактом ЛР4 (33 операции)
Для сохранения полной обратной совместимости с архитектурой ЛР4, тестами и MCP-сервером:
1. **Сохранение контракта `api/openapi.json`:**
   * Все **33 операции** из ЛР4 сохраняются в спецификации.
   * Роутеры FastAPI используют оригинальные канонические пути:
     - `POST /api/v1/auth/token` (авторизация с выдачей Bearer-токена как по логину/паролю, так и в режиме быстрого переключения демо-персон: `artem`, `kirill`, `maria_volunteer`, `gleb_org`);
     - `GET /api/v1/events` (постраничный каталог с фильтрацией по `status`, `event_type`, `venue_id`);
     - `GET /api/v1/events/{event_id}` (детальная карточка мероприятия);
     - `POST /api/v1/events` (создание события организатором);
     - `POST /api/v1/events/{event_id}/registrations` (регистрация слушателя, учет квоты и автоматическая постановка в `waitlist_entries` при исчерпании мест);
     - `GET /api/v1/me/tickets` (список билетов текущего пользователя);
     - `GET /api/v1/tickets/{ticket_id}` (детальный просмотр билета с HMAC-токеном);
     - `DELETE /api/v1/tickets/{ticket_id}` (отмена билета с автоматическим синхронным продвижением первого участника из листа ожидания в статус `registered`);
     - `POST /api/v1/events/{event_id}/check-ins` (верификация QR-билета волонтером с проверкой HMAC, фиксацией времени и защитой от повторного прохода HTTP 409);
     - `GET /api/v1/venues` (список аудиторий);
     - `GET /api/v1/health` (проверка работоспособности сервиса).
   * Остальные 22 операции спецификации ЛР4 (расписания, CFP доклады, команды, геокодинг, экспорт) поддерживаются в FastAPI в виде валидируемых роутов со сгенерированными эталонными ответами.
2. **Протокол динамического QR-билета и верификация:**
   * Формат криптографического токена: `v1.{ticket_id}.{user_id}.{hmac_sha256(ticket_id + user_id + event_id, SECRET)}`.
   * Мобильный экран билета генерирует активную визуальную анимацию (динамический таймер с секундами и защитой от скриншотов).
   * Сканер волонтера валидирует HMAC-подпись и статус в базе данных, гарантируя отсечение подделок и повторных проходов.
3. **Хранилище данных и переносимость (Render & Local):**
   * Основной движок: SQLite с автоматическим автосидированием демонстрационными данными при первом запуске (гарантирует немедленную готовность на Render без потери данных при рестартах контейнера).
   * Поддержка профиля PostgreSQL 16 в `compose.yaml` и валидация DDL в CI.
4. **Хостинг клиентов и CORS:**
   * Сервер FastAPI настраивает `CORSMiddleware(allow_origins=["*"])`.
   * Клиенты поставляются в двух режимах:
     1. Локально внутри FastAPI: `app.mount("/web")` и `app.mount("/mobile")`.
     2. Встраивание в портал GitHub Pages репозитория `CampusMeet` (`docs/pages/lab7.html`) с автоматическим определением базового адреса API.

### 4.4. Клиентские модули
* **Веб-клиент (`web/index.html` + `web/app.js`):**
  - Каталог событий с карточками: название, дата, аудитория, теги, прогресс-бар занятых мест.
  - Фильтры по категориям и строка быстрого поиска.
  - Кнопка бронирования с выводом интерактивного уведомления и полученного билета.
* **Мобильный клиент (`mobile/index.html` + `mobile/app.js`):**
  - Адаптивный экран смартфона (разрешение 375x812 pt, стиль iOS 18 / True Black AMOLED).
  - Отображение билета с активным тикающим QR-кодом, номером регистрации и кнопкой симуляции валидации на стойке прохода.

### 4.5. Контроль качества (Quality Gate) и CI/CD
* **Линтинг:** `flake8 --max-line-length=120 campusmeet tests`
* **Автотесты:** `pytest tests/ -v --cov=campusmeet`
* **SonarQube / SonarCloud:** Конфигурация ключа проекта `fpmi-hci-2026_CampusMeet-Server`, указание путей к исходникам и отчетам покрытия тестами.
* **GitHub Actions:**
  ```yaml
  name: CampusMeet Server CI
  on: [push, pull_request]
  jobs:
    test-and-quality:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4
        - uses: actions/setup-python@v5
          with: { python-version: '3.12' }
        - run: pip install -r requirements.txt -r requirements-dev.txt
        - run: flake8 campusmeet tests
        - run: pytest tests/ -v
        - name: Build Docker image
          run: docker build -t campusmeet-server:latest .
  ```

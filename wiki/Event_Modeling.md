# Проектирование системы методом Event Modeling (Методика Адама Димитрука)

В данном разделе представлена архитектурная спецификация экосистемы **CampusMeet / EventHub**, спроектированная по методологии **Event Modeling** (Адам Димитрук) на языке **PlantUML**. Метод ориентирован на строгое информационное моделирование «срезов» (Slices) системы в парадигме **Given-When-Then**, связывая пользовательские интерфейсы (UI/Wireframes), команды изменения состояния, неизменяемые бизнес-факты (Events) и модели чтения (Read Models / Views).

---

## 1. Концепция и базовые строительные блоки Event Modeling

Event Modeling рассматривает систему как непрерывную временную ось слева направо, разделенную на горизонтальные дорожки (lanes):
* **Верхняя дорожка (UI / Mockups / Wireframes):** Экранные представления и действия пользователей (триггеры).
* **Средняя дорожка (Commands & Read Models):** Синие блоки команд (намерения изменить состояние) и зеленые блоки представлений (снимки данных для экрана).
* **Нижняя дорожка (Events / Business Facts):** Оранжевые блоки событий, сохраненных в неизменяемый журнал (Append-Only Event Log).

### 4 фундаментальных шаблона проектирования (Slices):

```text
1. Command Pattern:     Trigger (UI) ──────► Command (Blue) ──────► Event(s) (Orange)
2. View Pattern:        Event(s) (Orange) ──► View / Read Model (Green) ──► UI Display
3. Automation Pattern:  Event ──► View ──► Automated Trigger ──► Command ──► New Event
4. Translation Pattern: Event (Source) ──► View ──► Translator Adapter ──► External Command ──► External Event
```

## 2. Спецификация срезов архитектуры CampusMeet (Slices)

Исходный файл: `docs/diagrams/puml/event_modeling/event_modeling_slices.puml`  
Векторный рендер: `docs/diagrams/puml/event_modeling/event_modeling_slices.svg`

### Срез 1: Регистрация слушателя (Command Pattern)
* **Назначение:** Реализует сценарий атомарного резервирования места на митап.
* **Структура цепочки:**
  - *Trigger:* Пользователь нажимает экранную кнопку «Зарегистрироваться» на карточке митапа в мобильном клиенте.
  - *Command (Синий):* `RegisterAttendee(event_id, user_id, timestamp)`.
  - *Event (Оранжевый):* `TicketReserved(ticket_id, quota_remaining)`.
* **GWT-семантика:**  
  *Дано:* Пользователь авторизован и мероприятие имеет свободные квоты.  
  *Когда:* Выполняется команда `RegisterAttendee`.  
  *Тогда:* В журнал событий записывается факт `TicketReserved`.

---

### Срез 2: Формирование витрины билета (View Pattern)
* **Назначение:** Проекция сохраненного состояния на экран смартфона пользователя.
* **Структура цепочки:**
  - *Event (Оранжевый):* Событие `TicketIssued(ticket_id, qr_payload, hmac_hash)`.
  - *View / Read Model (Зеленый):* Проекция `MyActiveTicketsReadModel`.
  - *UI Presentation:* Экран «Мой билет» в нативном мобильном приложении с QR-кодом, 6-значным резервным кодом и авто-яркостью 100%.
* **GWT-семантика:**  
  *Дано:* В системе существует факт `TicketIssued`.  
  *Когда:* Мобильный клиент опрашивает проекцию `MyActiveTicketsReadModel`.  
  *Тогда:* Экран отображает верифицированный билет даже при отключении сети (режим офлайн).

---

### Срез 3: Автоматическая ротация очереди Waitlist (Automation Pattern)
* **Назначение:** Автономное перераспределение освободившихся мест без участия человека.
* **Структура цепочки:**
  - *Event (Оранжевый):* Слушатель отменил регистрацию $\rightarrow$ событие `TicketCancelled(ticket_id)`.
  - *View (Зеленый):* Обновление модели чтения `WaitlistQueueView` (освободился 1 слот).
  - *Automated Trigger (Фиолетовый):* Фоновый процесс `QueueProcessorDaemon` обнаруживает свободное место и наличие кандидатов в очереди.
  - *Command (Синий):* Инициация команды `PromoteWaitlistGuest(next_user_id)`.
  - *New Event (Оранжевый):* Фиксация факта `TicketGrantedFromWaitlist(ticket_id, new_user_id)`.
* **Бизнес-ценность:** Нулевое время простоя мест при отказах гостей; автоматическое заполнение зала до 100% квоты.

---

### Срез 4: Доставка экстренного Push-вещания (Translation Pattern)
* **Назначение:** Мост трансляции внутренних бизнес-событий во внешние провайдеры доставки (Apple APNs / Google FCM).
* **Структура цепочки:**
  - *Event (Оранжевый - исходная система):* Организатор перенес аудиторию $\rightarrow$ событие `RoomChangedEvent(event_id, new_room="514")`.
  - *View (Зеленый):* Проекция `PendingPushBatchView` накапливает список push-токенов зарегистрированных слушателей.
  - *Translator Adapter (Фиолетовый):* Асинхронный воркер `FCMNotificationTranslator`.
  - *External Command (Синий):* Вызов внешнего API: `SendMulticastPayload(APNs/FCM)`.
  - *External Event (Оранжевый - внешняя система):* `PushDeliveredToDevice` (подтверждение доставки пакета шлюзом Apple/Google).

## 3. Преимущества Event Modeling для команды разработки

1. **Идеальная совместимость с BDD:** Каждый срез транслируется в автоматический интеграционный тест формата Cucumber / Behave.
2. **Точная оценка трудозатрат (Slicing):** Разработчик получает замкнутую спецификацию конкретного среза, включающую UI-экран, команду валидации, сохраняемое событие и его проекцию в БД.
3. **Отсутствие скрытых состояний:** Система прозрачна для аудита, так как вся история изменений формируется исключительно из неизменяемых фактов.

# Описание архитектуры системы с использованием подхода C4 Model (Саймон Браун)

В данном разделе представлена многоуровневая архитектурная модель программного комплекса **CampusMeet / EventHub**, разработанная по методологии **C4 Model** (Context, Container, Component, Code) Саймона Брауна с использованием библиотеки **C4-PlantUML**. Модель обеспечивает ступенчатую декомпозицию системы от глобального бизнес-окружения до низкоуровневых программных интерфейсов.

---

## 1. Концепция и уровни абстракции C4 Model

1. **Уровень 1: Системный контекст (System Context, C1):** Очерчивает границы программной системы CampusMeet, показывает внешних пользователей (акторов) и смежные сторонние системы.
2. **Уровень 2: Контейнеры (Containers, C2):** Описывает высокоуровневую топологию развертываемых приложений и хранилищ данных (Web SPA, Mobile App, API Gateway, Message Broker, RDBMS).
3. **Уровень 3: Компоненты (Components, C3):** Детализирует внутреннее устройство ключевого контейнера (API Gateway & Core Backend), выделяя контроллеры, сервисы и адаптеры.
4. **Уровень 4: Код (Code / Classes, C4):** Специфицирует объектную структуру и интерфейсы критического ядра системы — криптографического движка валидации билетов `TicketCryptoEngine`.

## 2. Уровень C1: Системный контекст (Context Diagram)

Исходный файл: `docs/diagrams/puml/c4/c4_context.puml`  
Векторный рендер: `docs/diagrams/puml/c4/c4_context.svg`

### Взаимодействие со средой:
* **Пользователи экосистемы:**
  - *Слушатель (Attendee):* Поиск мероприятий, регистрация в 1 клик, получение динамического QR-билета, персональная программа.
  - *Волонтер (Volunteer):* Высокоскоростной оптический чекин на входе (<500 мс).
  - *Организатор (Organizer):* Создание митапов, квотирование, модерация заявок спикеров CFP, экстренные Push-рассылки.
  - *Спикер (Speaker):* Подача тем докладов и файлов презентаций.
  - *Администратор площадки (Patron):* Согласование аудиторий корпуса и выгрузка аналитики явки.
* **Внешние облачные сервисы:**
  - *OpenStreetMap Nominatim API:* Геокодирование адресов площадок и определение точных географических координат.
  - *Nager.Date API:* Аудит производственного календаря и государственных праздников Беларуси для исключения накладок.
  - *Apple APNs & Google FCM:* Облачные шлюзы гарантированной доставки системных push-уведомлений на мобильные устройства.
  - *Telegram Bot Gateway:* Резервный канал оповещения команды организаторов и волонтеров.

## 3. Уровень C2: Диаграмма контейнеров (Container Diagram)

Исходный файл: `docs/diagrams/puml/c4/c4_container.puml`  
Векторный рендер: `docs/diagrams/puml/c4/c4_container.svg`

### Состав контейнеров экосистемы:
1. **Web Organizer Dashboard (Next.js 14, React, Tailwind CSS):** Десктопный клиент для администраторов и организаторов. Реализует сквозной поиск Omnibox `⌘K`, интерактивный Drag-and-Drop конструктор расписания и аналитические дашборды.
2. **Mobile Client & Scanner (React Native, Expo, TypeScript):** Кроссплатформенное мобильное приложение для iOS и Android. Содержит Offline-First модуль показа билета с авто-яркостью 100% и оптический сканер на базе AVFoundation / CameraX с временем распознавания <500 мс.
3. **Mobile Secure Vault (SecureStore & SQLite Cache):** Локальное шифрованное хранилище смартфона для кеширования JWT-токенов, билетов и открытых ключей мероприятий.
4. **API Gateway & Core Service (Python, FastAPI, Uvicorn):** Центральный асинхронный сервер бизнес-логики. Обеспечивает авторизацию OAuth2/JWT, криптографическую подпись билетов HMAC-SHA256 и REST API шлюз.
5. **Async Task Worker (Celery, Python):** Пул фоновых воркеров для тяжелых операций: пакетная отправка Push-уведомлений, периодическая синхронизация очередей и генерация аналитических отчетов в формате Excel.
6. **Message Broker & Cache (Redis 7):** In-memory хранилище очередей задач Celery, распределенный Rate Limiter и кеш горячих данных.
7. **Relational Database (PostgreSQL 16):** Основное реляционное хранилище данных (10 таблиц, транзакции ACID, внешние ключи, индексы).

## 4. Уровень C3: Диаграмма компонентов (Component Diagram)

Исходный файл: `docs/diagrams/puml/c4/c4_component.puml`  
Векторный рендер: `docs/diagrams/puml/c4/c4_component.svg`

### Декомпозиция контейнера API Gateway (FastAPI):
* **AuthController & Security:** Модуль аутентификации, генерация и валидация JWT access/refresh токенов, хеширование паролей алгоритмом bcrypt.
* **EventManagementController:** Контроллер жизненного цикла мероприятий, валидация лимитов квот Hard Cap и публикация в публичный каталог.
* **TicketCryptoEngine:** Ядро генерации динамических билетов. Формирует криптографическую подпись HMAC-SHA256 с индивидуальной солью события.
* **AttendanceCheckinService:** Сервис обработки потока сканирования, верификация статуса билета, фиксация волонтера и выявление попыток повторного прохода (дубликатов).
* **CFP & ScheduleManager:** Модуль приема заявок спикеров, загрузки презентаций и верстки программы по трекам.
* **GeoCalendarAdapter:** Асинхронный адаптер интеграции с внешними REST API (OSM Nominatim и Nager.Date).
* **NotificationDispatcher:** Диспетчер асинхронных уведомлений, формирующий задачи в очередь Redis для воркеров Celery.

## 5. Уровень C4: Диаграмма кода (Code Level Diagram)

Исходный файл: `docs/diagrams/puml/c4/c4_code.puml`  
Векторный рендер: `docs/diagrams/puml/c4/c4_code.svg`

### Детализация криптографического движка:
* **Интерфейс `ITicketSigner`:** Специфицирует методы формирования цифровой подписи `sign_ticket_payload()` и проверки подлинности `verify_ticket_signature()`.
* **Класс `HMACSHA256TicketEngine`:** Реализует криптографическую логику стандарта RFC 2104. Использует алгоритм SHA-256 со скользящим временным окном в 30 секунд для предотвращения атак воспроизведения.
* **Интерфейс `IOfflineCacheStorage`:** Определяет контракт доступа к локальной базе хешей устройства волонтера.
* **Класс `OfflineValidationScanner`:** Обеспечивает автономную работу оптического сканера, принимает решение о допуске (`CheckInDecision`) без обращения к сети и формирует батчи синхронизации.

### Промпт №1: Генерация пользовательских историй (User Story & BDD Generator)
```text
Ты — ведущий системный и бизнес-аналитик уровня Principal (CBAP). Твоя задача — разработать исчерпывающий набор требований в формате User Story для указанного функционального модуля.

Входные данные:
- Название продукта и домен: CampusMeet (студенческая экосистема митапов и хакатонов)
- Целевой модуль: {Название модуля, например, "Контроль входа и валидация билетов"}
- Роли пользователей: {Роли, например, "Волонтер-контролер, Слушатель, Организатор"}
- Технологические ограничения: Offline-First, время отклика сканера <500 мс.

Требования к генерации:
1. Формулируй каждую User Story строго по шаблону Майка Кона:
   "Как [роль пользователя], я хочу [действие/цель], чтобы [бизнес-ценность/результат]".
2. Для каждой User Story составь от 4 до 7 проверяемых критериев приёмки (Acceptance Criteria) по шаблону Given-When-Then (GWT / BDD).
3. Проверь каждую историю по критериям INVEST (Independent, Negotiable, Valuable, Estimable, Small, Testable).
4. Обязательно укажи платформенные различия для Web (доступность WCAG, мышь/клавиатура, сетки) и Mobile (тактильный Haptic отклик, камера, Safe Area, локальное шифрованное кеширование).
5. Определи приоритет по шкале MoSCoW с кратким обоснованием бизнес-эффекта и укажи зависимости от предшествующих историй.
Выведи результат в структурированном Markdown с таблицами.
```

### Промпт №2: Проектирование UML-диаграмм (PlantUML Diagram Architect)
```text
Ты — корпоративный архитектор программного обеспечения и эксперт по языку моделирования UML и инструменту PlantUML.

Задача:
Спроектировать валидную, визуально выверенную и семантически точную диаграмму {ТИП ДИАГРАММЫ: Use Case / Activity / Class / Sequence / Component / Deployment / ERD} для подсистемы: {Название подсистемы}.

Правила оформления кода PlantUML:
1. Начинай блок строго с @startuml и заканчивай @enduml.
2. Используй строгий corporate/neo-swiss визуальный стиль (monochrome false, shadowing false, чистые шрифты Helvetica/Arial, мягкие контрастные цвета: синий #2563EB, зеленый #16A34A, серый #334155, фон #F8FAFC).
3. Для Use Case: четко разделяй системные границы rectangle, используй стереотипы <<include>> и <<extend>> с логическими условиями в кавычках.
4. Для Activity: используй современный синтаксис (start, stop, if-then-else, дорожки |swimlane|, параллельные ветки fork-again).
5. Для Class: указывай модификаторы доступа (+, -, #), типы полей, методы с параметрами и возвращаемыми типами, а также множественности (1, 0..*, 1..*).
6. Для Sequence: используй участников с типами (actor, participant, database), активируй/деактивируй линии жизни (activate/deactivate), группируй альтернативы (alt/else) и параллельные потоки (par).
7. Для Deployment: моделируй реальную контейнерную и физическую топологию (ноды, артефакты, порты и протоколы).
8. Код должен компилироваться без предупреждений и ошибок парсера. Добавь заголовок title и краткую легенду при необходимости.
```

### Промпт №3: Формирование технической спецификации требований (SRS by Karl Wiegers)
```text
Ты — эксперт по разработке нормативных технических заданий на программные комплексы по стандартам IEEE 830, ISO/IEC/IEEE 29148 и методологии Карла Вигерса / Джой Битти ("Разработка требований к программному обеспечению").

Задача:
Сформировать раздел технического задания (SRS) для системы {CampusMeet} с глубокой проработкой нефункциональных требований, моделей данных и атрибутов качества.

Структура вывода:
1. Идентификация и границы подсистемы.
2. Функциональные требования с уникальными кодами (FR-XXX) и уровнем критичности.
3. Логическая модель данных и правила валидации бизнес-сущностей.
4. Внешние интерфейсы: UI, REST API эндпоинты, протоколы взаимодействия оборудования (видеокамера, Haptic отклик, Bluetooth/NFC).
5. Атрибуты качества системы:
   - Надежность и готовность (MTBF, MTTR, Offline-First устойчивость к потере сети);
   - Производительность (время отклика сканера <500 мс, пропускная способность чекина >=40 чел/мин);
   - Безопасность (алгоритмы HMAC-SHA256, защита от перехвата и атак повторного воспроизведения, хранилище SecureStore);
   - Юзабилити и доступность (WCAG 2.1 AA, зоны досягаемости одной рукой Thumb Zone).
6. Матрица трассируемости: привязка User Story -> Use Case -> Компонент архитектуры -> Тестовый сценарий.
Формат вывода: академический строгий стиль, однозначные термины без двусмысленностей ("должен", "обязан", "следует").
```

## 2. Демонстрация навыков ИИ-агента (AI Skills for System Analyst)

В ходе проектирования были задействованы современные когнитивные техники агентного анализа:

1. **Контекстная декомпозиция (Chain-of-Thought / Structured Slicing):**
   При анализе проблемы очередей на входе агент выделил скрытые ограничения: цокольные аудитории университетов экранируют радиосигнал (нет LTE). Из этого выведено нефункциональное требование: *«Офлайн-валидация билета не может обращаться к центральному серверу, следовательно, проверка подлинности должна быть асимметричной или базироваться на предварительно закешированном HMAC-секрете мероприятия»*.
2. **Семантическая валидация непротиворечивости (Self-Consistency Verification):**
   Агент выполнил сквозную перекрестную проверку между сущностями базы данных (`schema.sql`), диаграммами классов PlantUML и спецификациями Use Case:
   - Поле `secret_salt` в таблице `events` согласовано с методом `HMACSigner.sign()` на диаграмме классов и полем в полезной нагрузке динамического QR-кода на диаграмме последовательности.
   - Вместимость аудитории `Venue.fire_safety_capacity` согласована с валидатором квоты `Event.hard_cap_quota` в диаграмме деятельности.
3. **Генерация кросс-нотационных моделей:**
   Трансформация концептуальной модели из словесного описания параллельно в три визуальных языка:
   - **PlantUML** — для глубокого детального проектирования с типами данных и физическими нодами;
   - **Mermaid** — для легковесного интерактивного рендеринга на веб-портале документации;
   - **EventStorming / Event Modeling** — для анализа временных потоков событий и DDD-контекстов.

## 3. Расширенный список пользовательских историй (Сгенерирован с применением ИИ)

В дополнение к базовым 9 историям из Задания 1, с помощью промпт-инжиниринга синтезированы специализированные User Stories:

### US-10: Экспорт билета в нативный кошелек Apple Wallet / Google Wallet
* **Формулировка:**  
  *«Как владелец смартфона, я хочу в 1 клик добавить свой билет в Apple Wallet (`.pkpass`) или Google Wallet, чтобы вызывать пропуск двойным нажатием боковой кнопки блокировки без необходимости открывать приложение CampusMeet».*
* **Приоритет:** **Medium (Should Have)**.
* **Acceptance Criteria (GWT):**
  - **Дано:** Пользователь получил подтвержденный билет. **Когда:** Нажимает «Добавить в Apple Wallet». **Тогда:** Сервер генерирует криптографически подписанный пакет `.pkpass` с логотипом митапа, временем начала и координатами зала.
  - При приближении к координатам корпуса геофенсинг iOS автоматически выводит виджет билета на экран блокировки смартфона.

### US-11: Визуальный Drag-and-Drop конструктор расписания митапа
* **Формулировка:**  
  *«Как организатор, я хочу формировать программу выступлений перетаскиванием карточек докладов мышью в сетке таймлайна, чтобы визуально исключить пересечения параллельных треков и наглядно балансировать паузы на кофе-брейк».*
* **Приоритет:** **Medium (Should Have)**.
* **Acceptance Criteria (GWT):**
  - При перетаскивании доклада система подсвечивает доступные слоты зеленым цветом и блокирует занятые ячейки.
  - При возникновении наложения по времени между докладами в одном зале система выводит предупреждающую красную подсветку.
  - Изменения в тайминге автоматически сохраняются и обновляют публичную витрину программы за время <1 с.

### US-12: Автоматизированная выгрузка сводного аналитического отчета явки (CSV/Excel)
* **Формулировка:**  
  *«Как куратор площадки от деканата, я хочу выгружать сводную ведомость присутствия студентов с указанием курса, группы и точной секунды чекина в формат .xlsx, чтобы иметь официальный документ учета посещаемости для учебной части».*
* **Приоритет:** **Low (Could Have)**.
* **Acceptance Criteria (GWT):**
  - В отчете агрегируются поля: ФИО, факультет, учебная группа, статус прохода, точный таймстемп прохода, ФИО волонтера-валидатора.
  - Генерация файла для выборки до 500 человек происходит асинхронно в воркере Celery и занимает менее 1.5 секунд.

# Проектирование системы методом EventStorming (DDD & Нотация Альберто Брандолини)

В данном разделе представлена архитектурная спецификация экосистемы **CampusMeet / EventHub**, спроектированная на основе метода **EventStorming** (Альберто Брандолини) на языке **PlantUML**. Метод ориентирован на выявление доменных событий, команд, бизнес-правил и декомпозицию системы на ограниченные контексты (Bounded Contexts) предметно-ориентированного проектирования (Domain-Driven Design).

---

## 1. Концепция и цветовая семантика нотации EventStorming

EventStorming использует строгую цветовую грамматику «стикеров», моделирующую бизнес-процессы во времени:

| Элемент EventStorming | Цвет стикера | Hex / Стиль | Семантика в контексте CampusMeet |
|:---|:---:|:---:|:---|
| **Domain Event (Событие)** | Оранжевый | `#FFA726` | Бизнес-факт, произошедший в системе, формулируется строго в прошедшем времени (*«Билет выпущен»*, *«Проход зафиксирован»*). |
| **Command (Команда)** | Голубой | `#42A5F5` | Намерение пользователя или системы произвести действие, формулируется в повелительном наклонении (*«Зарегистрироваться»*, *«Отсканировать QR»*). |
| **User Role (Роль/Актор)** | Желтый (малый) | `#FFEE58` | Пользователь или роль, инициирующая команду (*«Слушатель»*, *«Волонтер»*, *«Организатор»*). |
| **Aggregate (Агрегат)** | Желтый (большой) | `#FFF59D` | Бизнес-сущность или кластер состояния, принимающий команду и порождающий событие (*«Квота митапа»*, *«Билет»*). |
| **Policy / Rule (Политика)** | Фиолетовый | `#AB47BC` | Реактивное автоматическое правило: *«Когда произошло событие X, ТОГДА выполнить команду Y»*. |
| **Read Model / View (Витрина)** | Зеленый | `#66BB6A` | Экранное представление или проекция данных, помогающая пользователю принять решение. |
| **External System (Внешняя система)** | Розовый | `#F06292` | Сторонний сервис ввода/вывода данных (*«OSM Nominatim»*, *«Nager.Date»*, *«APNs/FCM»*). |
| **Hotspot (Противоречие/Риск)** | Малиновый | `#E91E63` | Конфликт, критический барьер или узкое место процесса (*«В цоколе нет сети»*, *«Овербукинг»*). |

## 2. Уровень 1: Крупномасштабное исследование (Big Picture)

Исходный файл: `docs/diagrams/puml/event_storming/event_storming_big_picture.puml`  
Векторный рендер: `docs/diagrams/puml/event_storming/event_storming_big_picture.svg`

### Анализ сквозной хронологии жизненного цикла митапа:
1. **Фаза инициации:** Создание анонса, назначение квот, резервирование аудитории в деканате.  
   *Малиновая точка (Hotspot H1):* Риск пересечения бронирований аудитории с учебным расписанием университета.
2. **Фаза открытой регистрации:** Открытие приема заявок, бронирование мест участниками, исчерпание квоты и постановка в лист ожидания.  
   *Малиновая точка (Hotspot H2):* Риск «синдрома неявки» (No-Show rate до 35%), когда зарегистрированные гости не приходят и блокируют доступ другим.
3. **Фаза подготовки программы:** Подача заявок докладчиками CFP, утверждение тем программным комитетом, верстка сетки расписания.
4. **Фаза входного контроля (День события):** Открытие билетов на смартфонах, оптический чекин волонтерами, обнаружение попыток повторного прохода.  
   *Малиновая точка (Hotspot H3):* **Критический отказ сети** — цокольные этажи и массивные железобетонные перекрытия вуза полностью глушат радиосигнал 4G/LTE. Система обязана функционировать полностью автономно!
5. **Фаза проведения и закрытия:** Экстренные оповещения при сдвигах программы, завершение митапа и выгрузка аналитического отчета явки.

## 3. Уровень 2: Моделирование процессов (Process Modeling)

Исходный файл: `docs/diagrams/puml/event_storming/event_storming_process.puml`  
Векторный рендер: `docs/diagrams/puml/event_storming/event_storming_process.svg`

### Ключевые процессные цепочки:
1. **Процесс ротации очереди Waitlist:**
   - Команда `RegisterAttendee` $\rightarrow$ Агрегат `EventQuota` $\rightarrow$ Событие `QuotaExhausted`.
   - Реактивная политика `WaitlistPolicy`: *«При исчерпании квоты перенаправить запрос в очередь ожидания»*.
   - Команда `EnqueueWaitlist` $\rightarrow$ Агрегат `EventQuota` $\rightarrow$ Событие `AttendeeAddedToWaitlist`.
2. **Процесс оптического чекина:**
   - Команда волонтера `ScanQRCode` $\rightarrow$ Агрегат `Ticket` $\rightarrow$ События `TicketRedeemed` (успех) либо `DuplicateAttemptDetected` (дубликат).
   - Событие `TicketRedeemed` немедленно обновляет зеленую витрину чтения `LiveAttendanceDashboard`.
3. **Процесс внешней интеграционной валидации:**
   - Команда организатора `ConfigureEvent` $\rightarrow$ Агрегат `Event` $\rightarrow$ Событие `EventDraftCreated`.
   - Политика `ValidateExternalConstraintsPolicy` $\rightarrow$ Розовый стикер `OSM & Nager.Date API` $\rightarrow$ Событие `LocationGeocodedAndCalendarAudited`.

## 4. Уровень 3: Проектирование и Ограниченные контексты (Software Design)

Исходный файл: `docs/diagrams/puml/event_storming/event_storming_design.puml`  
Векторный рендер: `docs/diagrams/puml/event_storming/event_storming_design.svg`

### Выделенные Bounded Contexts (Ограниченные контексты DDD):

```text
┌─────────────────────────────────┐       ┌─────────────────────────────────┐
│  Ticketing & Quota Context      │       │  Access Control Context         │
│  (Управление квотами и билетами)│       │  (Оптический чекин и охрана)    │
│  - Aggregate: Ticket, Quota     │       │  - Aggregate: CheckInLog        │
│  - Events: TicketIssued,        │       │  - Events: PassAuthorized,      │
│            TicketCancelled      │       │            DuplicateBlocked     │
└────────────────┬────────────────┘       └────────────────┬────────────────┘
                 │                                         │
                 │ Event: TicketCancelled                  │
                 ▼ (Авто-повышение из Waitlist)            │
┌────────────────┴────────────────┐                        │
│  Notification Context           │◄───────────────────────┘
│  (Асинхронные Push-рассылки)    │   Event: DuplicateBlocked / AlertBroadcast
│  - Aggregate: Dispatcher        │
└─────────────────────────────────┘
```

1. **Ticketing & Quota Context:** Отвечает за инварианты целостности квот, атомарное бронирование мест, управление пулом билетов и листом ожидания.
2. **Access Control Context:** Изолированный контекст входного контроля. Обладает автономной копией публичных криптографических ключей событий для независимой валидации билетов без сетевой связи с центральной СУБД.
3. **CFP & Schedule Context:** Отвечает за прием тезисов докладов, файлы презентаций, модерацию спикеров и верстку расписания по залам и трекам.
4. **Notification Context:** Высоконагруженный асинхронный контекст доставки push-уведомлений через брокер очередей Redis и облачные шлюзы APNs/FCM.

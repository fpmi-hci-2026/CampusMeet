# Спецификация требований к программному обеспечению (SRS) по Карлу Вигерсу / IEEE 830

Настоящий документ представляет собой нормативное техническое задание (Software Requirements Specification, SRS) на разработку кроссплатформенной экосистемы **CampusMeet / EventHub**, структурированное в соответствии с международным стандартом **IEEE 830 / ISO/IEC/IEEE 29148** и методологией Карла Вигерса и Джой Битти (*«Разработка требований к программному обеспечению»*).

---

## 1. Введение (Introduction)

### 1.1. Назначение (Purpose)
Настоящий документ определяет полный перечень функциональных и нефункциональных требований, проектных ограничений, моделей данных и внешних интерфейсов для программного комплекса **CampusMeet (EventHub)**. Предназначен для команды разработчиков, инженеров по обеспечению качества (QA), системных архитекторов и преподавателей кафедры технологий программирования ФПМИ БГУ.

### 1.2. Соглашения, принятые в документах (Document Conventions)
* Все требования снабжены уникальными буквенно-цифровыми идентификаторами вида:
  - `FR-CAT-XX` — функциональные требования (Functional Requirements);
  - `NFR-CAT-XX` — нефункциональные требования (Non-Functional Requirements).
* Приоритеты требований ранжируются по методологии MoSCoW:
  - **[Must]** — критически обязательное требование первой очереди;
  - **[Should]** — важное требование, обязательное к релизу MVP;
  - **[Could]** — желательное дополнительное требование;
  - **[Won't]** — исключено из текущего цикла разработки.
* Степень нормативности выражается модальными глаголами: *«должен / обязана»* (строгое требование), *«следует / рекомендуется»* (желательное условие).

### 1.3. Границы проекта (Project Scope)
Экосистема CampusMeet включает:
1. Десктопный Web-кабинет организатора (Next.js 14) для управления мероприятиями, квотами, CFP и аналитикой;
2. Кроссплатформенное мобильное приложение (React Native / Expo) для участников (Offline-First билет) и волонтеров (оптический сканер прохода);
3. Серверный API-шлюз и бизнес-логику (FastAPI, PostgreSQL, Redis, Celery);
4. Интеграционные шлюзы к внешним открытым API (OpenStreetMap Nominatim, Nager.Date, Apple APNs / Google FCM).

### 1.4. Ссылки на стандарты (References)
* IEEE Std 830-1998: IEEE Recommended Practice for Software Requirements Specifications.
* ISO/IEC/IEEE 29148:2018: Systems and software engineering — Life cycle processes — Requirements engineering.
* Web Content Accessibility Guidelines (WCAG) 2.1 (W3C Recommendation).
* RFC 2104: HMAC: Keyed-Hashing for Message Authentication.

## 2. Общее описание (Overall Description)

### 2.1. Общий взгляд на продукт (Product Perspective)
CampusMeet представляет собой распределенную клиент-серверную систему, решающую критическую проблему хаотичной организации университетских и локальных IT-мероприятий. Система ликвидирует очереди на стойках регистрации, сбои при отсутствии интернета на площадке и овербукинг залов.

### 2.2. Классы и характеристики пользователей (User Classes and Characteristics)
1. **Слушатели (Attendees):** Студенты 1–5 курсов и IT-специалисты. Техническая грамотность — средняя и высокая. Используют смартфоны iOS/Android.
2. **Волонтеры (Volunteers):** Студенты-активисты на стойке входа. Работают в условиях высокого стресса и очередей; требуется максимально простой интерфейс сканера без лишних кликов.
3. **Организаторы (Organizers):** Лидеры студенческих сообществ и координаторы митапов. Используют десктопные ПК/ноутбуки с широкими экранами (1366px — 4K).
4. **Спикеры (Speakers):** Докладчики и эксперты. Требуют удобный инструмент подачи тезисов доклада и мониторинга тайминга.
5. **Кураторы площадок (Patrons):** Представители администрации вуза. Требуют прозрачную отчетность и аудит безопасности залов.

### 2.3. Операционная среда (Operating Environment)
* **Серверная инфраструктура:** Linux Ubuntu 22.04 LTS / Debian 12 в контейнерах Docker Engine 24+, СУБД PostgreSQL 16+, брокер Redis 7+.
* **Веб-клиент:** Современные браузеры (Google Chrome 115+, Safari 16+, Mozilla Firefox 115+, Microsoft Edge 115+).
* **Мобильный клиент:** iOS 15.0+ (Apple iPhone), Android 10.0+ (API level 29+) с тыловой камерой с автофокусом и разрешением не менее 720p.

### 2.4. Ограничения дизайна и реализации (Design and Implementation Constraints)
* Архитектурный паттерн мобильного билета: **Offline-First**. Никакое отсутствие сотовой связи не должно блокировать открытие билета и локальную проверку подписи.
* Время оптической валидации билета камерой смартфона: строго **< 500 миллисекунд**.
* Использование открытого исходного кода и бесплатных открытых API (OpenStreetMap, Nager.Date) без платных проприетарных подписок.

### 2.5. Предположения и зависимости (Assumptions and Dependencies)
* Предполагается, что волонтер перед сменой подключается к Wi-Fi для однократной загрузки открытого реестра билетов митапа.
* Предполагается, что часы мобильных устройств синхронизированы по NTP с точностью не хуже $\pm 60$ секунд.

## 3. Функции системы (System Features)

### 3.1. Функция: Каталог митапов и сквозной поиск Omnibox
* **Описание:** Публичная афиша событий с фильтрацией по типам, тегам и полнотекстовым поиском.
* **Требования:**
  - `FR-CAT-01` [Must]: Система должна выводить список опубликованных мероприятий с сортировкой по дате начала.
  - `FR-CAT-02` [Should]: Поиск по горячим клавишам ⌘K/Ctrl+K должен поддерживать исправление опечаток (расстояние Левенштейна $D \le 2$).
  - `FR-CAT-03` [Must]: Карточка мероприятия обязана отображать счетчик оставшихся свободных мест и бейдж статуса (Свободно / Waitlist / Регистрация закрыта).

### 3.2. Функция: Регистрация и динамический Offline-First билет
* **Описание:** Резервирование квот и генерация защищенного динамического пропуска.
* **Требования:**
  - `FR-TCK-01` [Must]: Резервирование слота должно выполняться атомарной транзакцией с проверкой `COUNT < hard_cap`.
  - `FR-TCK-02` [Must]: Система должна генерировать цифровую подпись билета по алгоритму HMAC-SHA256 с солью мероприятия.
  - `FR-TCK-03` [Must]: Мобильное приложение обязано кешировать билет в зашифрованное системное хранилище `SecureStore`.
  - `FR-TCK-04` [Should]: При открытии экрана билета система обязана программно повышать яркость экрана смартфона до 100%.

### 3.3. Функция: Оптический чекин и детекция дубликатов
* **Описание:** Потоковый контроль прохода волонтерами на входе.
* **Требования:**
  - `FR-SCN-01` [Must]: Скорость оптического распознавания QR-кода камерой должна составлять менее 500 мс.
  - `FR-SCN-02` [Must]: При успешном проходе система обязана давать зеленую световую индикацию, звуковой тон и тактильный вибро-клик.
  - `FR-SCN-03` [Must]: При попытке повторного прохода система обязана выводить предупреждающий желтый экран с указанием времени первого сканирования.
  - `FR-SCN-04` [Must]: Сканер должен функционировать автономно без доступа к интернету на основе локальной базы SQLite.

### 3.4. Функция: Внешние интеграции (Геокодинг и Календарь)
* **Описание:** Автоматизация проверки адресов и дат.
* **Требования:**
  - `FR-EXT-01` [Should]: При вводе текстового адреса система обязана запрашивать координаты через OSM Nominatim API.
  - `FR-EXT-02` [Should]: При выборе даты система обязана опрашивать Nager.Date API и предупреждать о праздничных нерабочих днях РБ.

### 3.5. Функция: Экстренное оповещение и фоновые очереди
* **Описание:** Оперативная рассылка важных сервисных сообщений.
* **Требования:**
  - `FR-NTF-01` [Must]: Организатор должен иметь возможность отправить приоритетный Push всем участникам в 1 клик.
  - `FR-NTF-02` [Must]: Доставка пакета уведомлений до 500 пользователей через Celery/Redis должна занимать не более 3 секунд.

## 4. Требования к данным (Data Requirements)

### 4.1. Логическая модель данных (Logical Data Model)
Реляционная структура включает 10 нормализованных таблиц (3НФ):
`users`, `venues`, `events`, `tickets`, `check_ins`, `waitlist`, `tracks`, `sessions`, `hackathon_teams`, `team_members`. Схема зафиксирована в DDL-скрипте базы данных.

### 4.2. Словарь данных (Data Dictionary)
* `ticket_code`: Уникальная символьная строка формата `CMP-[A-Z0-9]{3}-[A-Z0-9]{3}` (например, `CMP-AI9-421`).
* `hmac_signature`: 64-символьная шестнадцатеричная строка HMAC-SHA256 подписи полезной нагрузки.
* `hard_cap`: Целочисленный жесткий лимит мест, $1 \le hard\_cap \le 500$.
* `fire_safety_capacity`: Максимально допустимая вместимость зала по нормам МЧС. Инвариант: $hard\_cap \le fire\_safety\_capacity$.

### 4.3. Требования к сохранению, целостности и утилизации данных
* **Целостность:** Каскадное удаление запрещено для таблиц аудита (`check_ins`, `tickets`). Используется мягкое удаление (Soft Delete с полем `deleted_at`).
* **Резервное копирование:** Автоматический ежедневный snapshot базы данных PostgreSQL с глубиной хранения 30 суток.
* **Утилизация:** Персональные данные участников (email, телефон) анонимизируются по истечении 1 года после завершения мероприятия по регламенту GDPR / Закона о защите персональных данных РБ.

## 5. Требования к внешним интерфейсам (External Interface Requirements)

### 5.1. Пользовательские интерфейсы (User Interfaces)
* **Web UI:** Адаптивный веб-интерфейс в стилистике Neo-Swiss (шрифты Inter/Roboto, строгая геометрия, акцентный синий `#2563EB`, статус зеленый `#16A34A` и красный `#DC2626`). Поддержка светлой и темной тем.
* **Mobile UI:** Соответствие гайдлайнам Apple Human Interface Guidelines (iOS) и Google Material Design 3 (Android). Соблюдение эргономики Thumb Zone (все ключевые интерактивные элементы в нижней трети экрана).

### 5.2. Программные интерфейсы (Software Interfaces)
* **REST API:** Спецификация OpenAPI 3.0 / Swagger доступна по адресу `/docs`. Обмен данными строго в формате JSON, кодировка UTF-8.
* **OpenStreetMap Nominatim:** HTTP GET с обязательным заголовком `User-Agent: CampusMeet/1.0`.
* **Nager.Date API:** HTTP GET `https://date.nager.at/api/v3/PublicHolidays/{Year}/BY`.

### 5.3. Интерфейсы оборудования (Hardware Interfaces)
* **Камера:** Доступ к сенсору через системные API AVFoundation (iOS) / CameraX (Android). Частота захвата кадров не менее 30 fps, автофокусировка на дистанции от 15 см.
* **Вибромотор:** Использование нативных Haptic Feedback API: `UIImpactFeedbackGenerator(style: .medium)` на iOS, `VibrationEffect.createOneShot()` на Android.

### 5.4. Коммуникационные интерфейсы (Communications Interfaces)
* Все внешние сетевые взаимодействия осуществляются строго по защищенному протоколу **HTTPS (TLS 1.3)** с шифрованием AES-256-GCM.
* Для живого обновления статистики явки на десктопном дашборде используется протокол **WebSocket (WSS)**.

## 6. Атрибуты качества системы (Quality Attributes)

### 6.1. Удобство использования (Usability)
* Соответствие стандарту доступности **WCAG 2.1 Level AA**: коэффициент контрастности текста к фону не менее $4.5:1$.
* Минимальный физический размер кликабельных областей (Touch Targets) на мобильных устройствах — не менее $44 \times 44$ pt.
* Индекс юзабилити System Usability Scale (SUS) по итогам тестирования — не ниже 80 баллов.

### 6.2. Производительность (Performance)
* Время отклика оптического сканера от попадания QR в видоискатель до выдачи результата: $\le 500$ мс.
* Время рендеринга экрана офлайн-билета из защищенного кеша: $\le 300$ мс.
* Время ответа API бронирования билета под нагрузкой 50 rps: 95-й перцентиль $\le 400$ мс.

### 6.3. Надежность и отказоустойчивость (Reliability & Fault Tolerance)
* Коэффициент доступности серверной части (Availability): не менее $99.8\%$ в дни проведения мероприятий.
* **Offline-First устойчивость:** 100% работоспособность предъявления и валидации билетов при полном обрыве интернет-связи на площадке.

### 6.4. Безопасность (Security)
* Защита паролей: хеширование алгоритмом `bcrypt` с фактором стоимости (work factor) не менее 12.
* Защита билетов от подделки: цифровая подпись HMAC-SHA256 с секретной солью события, недоступной клиентам.
* Защита от перехвата: сессионные JWT-токены с коротким временем жизни (15 минут) и безопасными Refresh-токенами в HTTP-Only Cookie.

## Приложение А. Глоссарий терминов

* **CFP (Call for Papers):** Процедура сбора и модерации заявок от потенциальных докладчиков мероприятия.
* **Hard Cap:** Жестко зафиксированный предел количества зарегистрированных участников митапа.
* **Waitlist (Лист ожидания):** Автоматизированная очередь пользователей, желающих попасть на митап при освобождении мест.
* **Offline-First:** Архитектурная концепция, при которой приложение сохраняет полную функциональность ключевых сценариев при отсутствии сети.
* **HMAC (Hash-based Message Authentication Code):** Механизм аутентификации сообщений с использованием криптографических хеш-функций и секретного ключа.
